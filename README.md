# Sales Data ETL Pipeline (PySpark)

A batch ETL pipeline built with PySpark that ingests messy raw sales data,
cleans and validates it, and writes it out as partitioned Parquet — the same
pattern used for real data lake / data warehouse ingestion jobs.

This is a **practice project** built to learn PySpark and data-lake-style
pipeline design; it runs against the local filesystem here but is structured
so it can be pointed at real AWS S3 with a small config change (see below).

## What it does

```
raw_zone/sales_raw.csv          (messy, synthetic source data)
        │
        ▼
scripts/etl_pipeline.py         (PySpark: extract → transform → load)
        │
        ▼
processed_zone/
  ├── sales_fact/                (partitioned by order_year, order_month)
  └── region_monthly_summary/    (pre-aggregated summary table)
```

**Extract** — reads the raw CSV with an explicit schema (`StructType`), not
`inferSchema=True`, since silently-inferred types are a common source of bugs
against real upstream data.

**Transform** handles realistic raw-data problems, on purpose seeded into the
synthetic dataset:
- Deduplicates exact-duplicate rows (simulates upstream retry/resend duplicates)
- Standardizes inconsistent categorical casing (`"south"`, `"SOUTH"`, `"South"` → `"South"`)
- Filters out rows with missing region or invalid/negative quantity, while
  counting how many rows were dropped (a basic data-quality check, not a silent drop)
- Parses three different raw date formats into one canonical date column
- Derives a `revenue` column and `order_year` / `order_month` partition keys

**Load** writes two Parquet outputs:
- `sales_fact/` — the cleaned, partitioned fact table (Hive-style partitioning
  by `order_year=YYYY/order_month=M/`, the standard layout for querying via
  Athena, BigQuery external tables, or Spark SQL)
- `region_monthly_summary/` — a small pre-aggregated table (revenue, units
  sold, order count by region/month) of the kind a BI tool would query directly

## Running it

```bash
pip install pyspark
python scripts/generate_raw_data.py   # (re)generates raw_zone/sales_raw.csv
python scripts/etl_pipeline.py        # runs the ETL job
```

Requires Java 8+ (Spark's dependency) and Python 3.9+.

## Running against real S3

The pipeline logic doesn't change — only the storage layer does:

1. In `etl_pipeline.py`, change `RAW_PATH` / `OUTPUT_PATH` to `s3a://your-bucket/raw/...`
   and `s3a://your-bucket/processed/...`
2. Add the S3A connector and AWS credentials to the Spark session config:
   ```python
   .config("spark.jars.packages", "org.apache.hadoop:hadoop-aws:3.3.4")
   .config("spark.hadoop.fs.s3a.access.key", os.environ["AWS_ACCESS_KEY_ID"])
   .config("spark.hadoop.fs.s3a.secret.key", os.environ["AWS_SECRET_ACCESS_KEY"])
   ```
3. Alternatively, run the pipeline locally as-is and use `scripts/s3_utils.py`
   to sync the `processed_zone/` output up to a real bucket afterward:
   ```bash
   pip install boto3
   export SALES_ETL_BUCKET=my-sales-etl-bucket
   python scripts/s3_utils.py
   ```

## Why the data is synthetic

`raw_zone/sales_raw.csv` is generated by `scripts/generate_raw_data.py` rather
than pulled from a public dataset, so the messiness (duplicates, inconsistent
casing, mixed date formats, missing values) is deliberate and reproducible —
useful for demonstrating specific cleaning logic rather than relying on
whatever a random dataset happens to contain.

## Tech stack

Python, PySpark (DataFrame API, partitioned Parquet writes), boto3 (S3 upload),
schema-on-read design, batch ETL pattern.

## Honest scope note

This is a learning/practice project, not a production system — there's no
orchestration (Airflow/Step Functions), no incremental/streaming ingestion,
and no automated tests yet. Those are natural next steps if this pipeline
were extended further.
